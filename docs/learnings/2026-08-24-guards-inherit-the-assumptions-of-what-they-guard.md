fact: A guard authored at the same time, by the same author, as the thing it guards tends to inherit that thing's assumptions, and therefore fires only on mistakes nobody was going to make. Three instances in two builds of this repo, each found by a DIFFERENT reviewer and each green until someone attacked it: (1) a self-mapper no-op gate parameterised at k=1, the degenerate value, could not see an inference-time feature-order reversal at all -- the bug it existed for was invisible at its own setting (see [[2026-08-23-degenerate-parameter-gate-is-blind]]); (2) CLI tests asserting `--help` exits 0 and contains a flag string pass unchanged if the flag is parsed and then never wired into any logic -- they test that a flag is SPELLED correctly, not that it DOES anything, and mutating `resolve_masks` to ignore `--n-train` left every one of them green; (3) a learning-curve summarizer refused point sets whose `holdout` fields disagreed, but nothing wrote those files, so the field would have been hand-typed during transcription -- the guard could only catch a typo made in the act of typing, never a point genuinely fitted against a different range. The common shape is that the guard and the artifact share a premise, so the guard tests the premise's consistency with itself rather than the artifact's correctness. Two cheap countermeasures, both used successfully here: run the guard at a NON-degenerate parameter setting (the k=1 gate became a k=3 gate and immediately caught both layer-order and head-order flips), and make the guard consume a value the artifact EMITS rather than one a human retypes (fit_mapper now writes the curve point itself, so `holdout` is the range the fit actually used). The general test to apply before trusting any guard: if the thing it guards were broken, would its output differ? If not, it is decoration.
