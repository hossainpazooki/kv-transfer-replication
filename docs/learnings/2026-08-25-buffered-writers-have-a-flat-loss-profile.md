fact: `kvt.data.dump_kv` accumulates every layer of every sequence in memory and writes only after its loop completes, so its loss profile is FLAT: a kill at 99% costs exactly as much as a kill at 1%. This is not hypothetical here -- a 420-sequence dump was killed 85% through its target half and produced zero bytes for that half, discarding roughly 75 minutes of compute, while the source half (which had finished its loop) was fully intact at 12 GB. The same buffering also holds about 12 GB resident at that scale, so streaming would relieve memory pressure as well as truncation risk. Two design consequences worth carrying: (a) a long-running writer should either write incrementally per unit of work or advertise plainly that partial progress is unrecoverable, because an operator watching a progress bar at 85% will reasonably assume 85% of the value is banked, and here none of it is; (b) when estimating whether to start such a job, the relevant question is not "how long does it take" but "how long is the window in which an interruption costs everything", and for this function those are the same number. What did NOT go wrong is worth recording too, because it is the difference between an expensive annoyance and a corrupted result: `KVDump.load` refuses an incomplete dump with `FileNotFoundError` rather than loading a truncated one, so there is no silent-corruption path from a killed dump into downstream numbers -- verified explicitly rather than assumed.
